\title{Autonomous Repository Engineer:\\
A Verified Tool-Using Coding Agent with Deterministic Governance}

\author{\IEEEauthorblockN{Vaibhav Mahore}
\IEEEauthorblockA{\textit{Undergraduate Programme, Mathematics and Computing}\\ \textit{Indian Institute of Science (IISc), Bengaluru, India}\\ mvaibhav@iisc.ac.in}}

\maketitle

\begin{abstract}
LLM-based coding agents typically fail in one of three ways: they parse
free-text tool calls until the model produces a malformed one, they hand the
model a shell, or they accept the model's claim that a task is complete.
This paper presents the Autonomous Repository Engineer, a coding-agent
runtime organized around an explicit governance principle: the model
proposes actions, the runtime validates and executes them, the repository
state provides observations, and completion is accepted only on verification
evidence the runtime gathers itself. A deterministic state machine with nine
states (INIT, ANALYZE\_REPO, PLAN, ACT, OBSERVE, REPLAN, VERIFY, COMPLETE,
FAILED) wraps a pluggable planner. \ToolCount{} built-in tools are invoked only through
schema-validated calls, subject to AUTO/ASK/DENY permission policies and a
workspace path jail; the single execution tool runs pytest with an
allowlist of flags and paths. VERIFY restores the files the task protects,
re-runs the suite and accepts completion only on exit status 0 backed by a
test report with passing tests. Agent-written code runs in a sandbox: by
default a fresh Docker container per test run with no network and a
read-only workspace, otherwise a local backend with resource limits. With a
deterministic planner that replays known fixes, the agent verifies
\BenchVerified{} of \BenchTasks{} multi-file benchmark tasks with
\BenchFailedCalls{} failed tool calls, and the committed results regenerate
byte for byte on Windows and Linux and under either sandbox. An earlier live
Gemini 2.5 Flash planner verified \LiveVerified{} of the \LiveTasks{} tasks
it was run on. Of \JailDockerTotal{} adversarial tool calls against the
Docker sandbox, \JailDockerRejected{} are rejected before anything runs and
\JailDockerContained{} run without gaining anything; the
\JailDockerResidual{} residual, code under test forging its own test
report, happens inside the test process and no sandbox can prevent it.
\end{abstract}

\section{Introduction}
Repository-level coding agents promise automation of small engineering
tasks: fixing a bug, repairing a failing test, adding coverage, or
refactoring an interface. Deploying an LLM for these tasks exposes three
recurring failure modes. First, \emph{interface fragility}: models
hallucinate tool names, omit required arguments, or misuse types, and a
runtime that parses free text crashes with them. Second, \emph{excessive
authority}: giving a model a shell prompt couples its correctness to host
security. Third, \emph{unverified completion}: a model can assert success
regardless of repository state, and a pipeline that trusts the assertion
automates nothing reliable.

Prior agent designs address these partially. ReAct-style loops
\cite{yao2023react} interleave reasoning and acting but leave execution
policy implicit. Toolformer \cite{schick2023toolformer} learns tool
invocation but targets self-supervised API use rather than repository
mutation under governance. CodeAct \cite{wang2024codeact} lets the model act
by writing executable code, which maximizes expressiveness and makes the
execution sandbox the whole safety boundary; this work takes the opposite
position and narrows what the model can ask for. SWE-bench
\cite{jimenez2024swebench} establishes that repository-level fixing is hard
at scale, but its harness measures capability, not the safety architecture
around a model.

The Autonomous Repository Engineer treats governance as the primary design
object. Its principle, enforced in code rather than prompt text, is:

\begin{quote}
\emph{The model proposes actions. The runtime validates and executes them.
The repository state provides observations. Completion is accepted only
after verification evidence.}
\end{quote}

The contributions are: (1) a planner/executor split in which every planner
output flows through one validation pipeline regardless of whether the
planner is a deterministic script or a live LLM
(Section~\ref{sec:overview}); (2) a tool layer with typed schemas,
permission policies, a lexical workspace jail and a flag-level allowlist for
test execution (Section~\ref{sec:tools}); (3) a state-machine runtime with
step, replan and planner-error budgets and a verification gate that the
planner cannot steer (Section~\ref{sec:runtime}); (4) a reproducible
multi-file benchmark, a live Gemini run recorded separately, and generated
adversarial evidence (Section~\ref{sec:eval}); and (5) an explicit account
of residual risks (Section~\ref{sec:limits}).

\section{System Overview}
\label{sec:overview}
Fig.~\ref{fig:pipeline} shows the division of authority. The planner (scripted
recipes, a recorded replay, or an LLM over an OpenAI-compatible endpoint)
emits one structured proposal per turn: a tool name and an argument object,
or a \texttt{done} declaration. The runtime alone decides what happens:
known tool, schema-conformant arguments, permission policy, and workspace
containment are all checked before any effect; rejected proposals become
observations returned to the planner rather than exceptions. The state
machine (Fig.~\ref{fig:fsm}) advances through ANALYZE\_REPO, PLAN, ACT and
OBSERVE, and then
either back to PLAN, to REPLAN on a failing test run, or to VERIFY, where the
runtime runs the suite itself. COMPLETE is reachable only from VERIFY. Step,
replan and consecutive planner-error budgets bound every run, and exhausted
budgets end in FAILED with a full trace.

The machine is strict: transitions not present in the adjacency table raise
errors rather than drifting, and the agent state (actions, observations,
test results, budgets, files changed, model usage) is serializable to JSON,
so every run leaves a reviewable artifact.

\section{Tool Layer}
\label{sec:tools}
The agent can call exactly \ToolCount{} built-in tools: \ToolList. Each is
declared as a specification containing its name, description, permission
class, typed arguments with ranges and size caps, and the arguments that are
paths. The registry rejects unknown tools, missing or mistyped arguments
(booleans are not integers), out-of-range values and unknown keys before
anything executes.

\textbf{Workspace jail.} Path arguments are jailed centrally, before the
tool runs, in two steps. The text is validated first, without touching the
filesystem: absolute, rooted, UNC, device and drive paths are rejected, as
are \texttt{..} above the root, a colon in any component (alternate data
streams), trailing dots or spaces, reserved device names and any
\texttt{.git} component. Only then is the path joined to the workspace, and
the target must equal its own real path:
\begin{lstlisting}
target = workspace.joinpath(*path_components(raw))
if normcase(realpath(target)) != normcase(target):
    raise JailViolation("goes through a link")
\end{lstlisting}
This refuses symbolic links and junctions anywhere on the way. Checking the
text first matters on Windows, where merely resolving a UNC path contacts
the named host. \texttt{search} and \texttt{list\_tree} skip links, and
writes re-check the target immediately before opening it.

\textbf{Unambiguous mutation.} \texttt{apply\_edit} replaces exactly one
occurrence of an exact string: zero matches and multiple matches are both
errors. \texttt{write\_file} refuses to overwrite existing files. The agent
may not write pytest control files (\texttt{conftest.py},
\texttt{pytest.ini}, \texttt{pyproject.toml}, \texttt{*.pth} and similar)
or any path the task protects, such as the existing tests of a bug-fix task.

\textbf{Test execution.} \texttt{run\_tests} is the only execution tool. The
command must be \texttt{python -m pytest} followed by flags from a short
allowlist and test paths that exist inside the workspace; argument files and
shell syntax are refused. The runtime then builds the real command itself:
its own interpreter with \texttt{-P}, so a planted \texttt{pytest.py}
cannot shadow pytest, the cache plugin disabled, root and conftest search
pinned to the workspace, no shell, an environment reduced to an allowlist
(no API keys), a deadline that kills the whole process tree, and a bounded
output buffer. Output passes through a redactor that removes credential
values and absolute host paths before it reaches the trace or the planner.
\texttt{git\_diff} is computed in-process against a snapshot taken at the
start of the run, so no git binary or repository configuration is involved.

Permission classes (READ\_ONLY, MUTATING, EXECUTION) map to policies
(AUTO, ASK, DENY). The default is AUTO for all three classes. Under ASK, only
an explicit approval allows a call; a missing or failing approver denies it.
Rejections are first-class observations: they are recorded in the trace and
returned to the planner as history, so a malformed proposal costs a turn,
not a crash.

\section{Runtime and Verification}
\label{sec:runtime}
The runtime loop maintains three budgets: a step budget (40), a replan
budget (4), and a budget of three consecutive planner errors, so the worst
case of a confused planner is bounded in steps, cost, and damage. A failed
test run transitions OBSERVE to REPLAN, which returns to PLAN or, with no
replans left, ends the run in FAILED. Each replan passes the planner the
reason and the end of the test output, where pytest reports failures.

On a \texttt{done} proposal the runtime enters VERIFY. It first restores the
protected paths and pytest control files from the starting snapshot,
whatever their size, and removes links and bytecode caches created during
the run; then it runs the task's suite with a fresh bytecode cache and a
JUnit report written outside the workspace. Verification passes only if the
exit status is 0 and the report shows at least one passing test and no
failures, so a suite that collects nothing, or code that ends the process
early with status 0, does not pass. For the task whose goal is to add tests,
the runtime also applies three seeded mutants to the protected code under
test, each of which must make the new tests fail (rejecting vacuous tests),
and two behaviour-preserving edits, which must leave them passing
(rejecting tests that only pin the file's hash). The restore step runs again
around every such run. The planner's claim is never consulted. Files changed by successful
edits are tracked by their workspace path, and the full state serializes to
a JSON trace.

The planner interface has four implementations, each with a stated role.
The \texttt{ScriptedPlanner} replays per-task recipes that already
contain the fix: it is a test fixture that exercises the runtime at zero
cost, and it solves nothing. \texttt{NativeToolPlanner}, the default for
models, uses each provider's native function calling (Gemini, OpenAI,
Anthropic or a local OpenAI-compatible server) with tool schemas generated
from the same specifications the registry enforces, answers every call id
with the runtime's observation, and compacts old tool results to fit a
context budget. The earlier \texttt{LLMPlanner}, kept for endpoints without
function calling, packages the task, the
repository listing, the tool catalog, any replan reason and the last ten
history entries into a prompt and parses a JSON reply; proposals then pass
through the identical validation pipeline. \texttt{RecordedPlanner} replays
captured actions for tests without network access.

files byte for byte under the local and the Docker sandbox; this was
checked on Windows and in Linux containers, and CI repeats the check. Because the recipes contain the answers,
this benchmark measures the runtime machinery (validation, state
transitions, verification and trace capture) and nothing about model

\subsection{Adversarial Evidence}
A generator script replays hostile tool calls against a real registry and
one sandbox backend,
each in a fresh workspace with a secret directory beside it, a directory
link pointing at that secret, protected tests and a repository whose git
configuration would run a hook. Fig.~\ref{fig:attacks} and
Table~\ref{tab:attacks} summarize the outcomes; the test suite re-runs the attacks and requires the committed
evidence to match exactly with no breach. Two independent reviews found
further faults (among them a workspace file named like a pytest argument
file, planted bytecode that replaced a protected test, a patch from an
incomplete diff that could delete files, and links followed when copying);
all are fixed, and those expressible as tool calls are in the evidence.
Further attacks target the sandbox itself: reading or writing host files,
the network, a process that outlives the run, memory, a fork bomb, filling
the disk, a conftest planted during a run, and forging the report. Under the
local backend several of them are documented residuals; under Docker all are
contained except report forging, which happens inside the test process on
every backend.

\section{Limitations}
\label{sec:limits}
(1) The scripted planner is a fixture; beyond the \LiveTasks{} live tasks, the
benchmark says nothing about model-driven competence. (2) Without Docker,
test execution is code execution on the host: the local backend's limits
protect the runtime, not the host's files or network, and a process that
leaves the tree on purpose (a new session on POSIX, WMI on Windows) escapes
the tree kill. (3) Verification runs the code under test in the same
process as pytest, so code written to forge the test report on purpose
could still pass on any backend, and on the add-a-test tasks a test that
inspects the source text for specific tokens can pass the mutant and
neutral-edit checks. (4) Under the local backend, write-time link checks
narrow but do not close the race with leftover test code; under Docker the
workspace is read-only to tests. (5) Multi-file patches are applied all or
nothing, but successive tool calls are not one transaction; the trace is
the review artifact. (6) Tool output reaches the
planner verbatim apart from redaction of credentials and host paths, so
prompt-injection resistance depends on the planner; the runtime bounds what
an injected instruction can do. (7) The tool set is intentionally minimal.

\section{Conclusion}
The Autonomous Repository Engineer argues that the interesting engineering
problem in coding agents is the governance around the model: typed tool
schemas with unambiguous mutation semantics, a jail and an argument-level
allowlist that keep the planner's own calls inside the workspace, budgets
that bound every run, and a verification gate the planner cannot steer. The
deterministic benchmark shows the machinery working
\BenchVerified/\BenchTasks{} with \BenchFailedCalls{} failed tool calls and
reproducible results; the earlier live Gemini run shows a real model's
proposals surviving the same pipeline \LiveVerified/\LiveTasks; and the adversarial
evidence states what is stopped and what is not. The project's limits
(fixture planner, report forging, a still small benchmark) are part of its
published specification.\footnote{\url{https://github.com/vaibhav3000/repo-engineer}}
